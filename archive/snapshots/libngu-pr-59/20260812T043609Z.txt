Fixes the root cause of the 2026-07-31 Coldcard "limited entropy" advisory inside libngu itself: random.c tested #ifndef MICROPY_HW_ENABLE_RNG, so boards defining it as (0) passed the guard and silently linked upstream MicroPython's pseudo-random fallback rng_get(). The firmware hotfix worked around this at the integrator level; this PR removes the trap at the source.
Changes
Fail-closed backends. STM32 builds stop unless the integrator attests -DNGU_STM32_RNG_GET_IS_HARDWARE=1 (checked by value — absent, 0, and wrong all fail). ESP32 likewise requires an entropy-lifecycle attestation and is intentionally unavailable until someone with hardware validates it. Linux moves random() → getentropy(); unknown targets don't build; the 0x5a5a5a5a fallback is gone.
Yasmarang → NIST SP 800-90A §10.1.2 HMAC_DRBG (SHA-256). Auto-seeded from 64 bytes of raw entropy on first use; every output word still XORed with a fresh entropy word. All outputs — including private-key generation in k1.c — share one checked path (uint32()/uniform() previously bypassed the stuck-TRNG check).
Entropy health rule (pure, testable module): repeats/oscillation fault with OSError, history persists across calls, STM32 zero words refused (timeout-conflated).
reseed() accepts bytes of any length and mixes into the full state (was: a 32-bit funnel that truncated Coldcard's 40 secure-element bytes to 4). reseed(int) still works.
Also fixed: negative bytes() count heap overwrite, one-bit-wide uniform() mask, threads-without-GIL now refused at compile time.
Testing
make tests now runs: official NIST CAVP vectors through both SHA-256 backends (mbedtls + cifra), deterministic health-rule tests, and negative compile gates proving every attestation/thread misconfiguration fails to build (ngu_tests: make cavp / health / gates).
Notes for reviewers
Deliberately build-breaking for STM32 integrators — one truthful -D flag fixes it. Coldcard firmware needs it on its next pin bump (true post-hotfix); output streams change (no determinism contract existed).
Known gaps, on purpose: no deterministic RNG test mode in production code; inherited cifra signed-shift UB (predates branch, upstream fix being prepared separately); Linux/ESP32 compile-verified only, not built here.
Disclaimer
This branch was developed with substantial LLM assistance, then adversarially reviewed over multiple rounds. It is deliberately structured so correctness doesn't depend on trusting the author: the DRBG is verified against official NIST CAVP vectors on both SHA-256 backends, every fail-closed claim has a negative compile test (make gates), and the health rule has deterministic host tests. Nevertheless, thorough maintainer review is expected.

Self-contained core for the RNG rework that follows: K/V state machine
with instantiate, mixing reseed, and backtracking-resistant generate.
No heap allocation and no failure paths -- HMAC is built directly on
the SHA-256 backend the rest of libngu already uses (mbedtls or cifra,
as in hash.c), because mbedtls' HMAC layer allocates and hardware SHA
(MBEDTLS_SHA256_ALT) can fail at runtime; the latter is refused at
compile time until a target proves its no-fail contract. Reseed
interval and prediction resistance are deliberately omitted and
documented: the consumer (random.c, next commits) mixes fresh entropy
into every output instead. Secret-bearing temporaries are wiped via a
volatile-store helper the optimizer cannot elide.

'make tests') against official NIST CAVP vectors -- 12 vectors plus 2
derived partial-block KATs, run through BOTH SHA-256 backends. The
vector extractor cross-checks every vector against an independent
pure-python reference before emitting; vectors are checked in with
provenance.

88f7b5a
A word matching either of the two previously accepted words is refused:
catches a source stuck on one value and one oscillating between two (a
dying ring oscillator). History starts zeroed, so a first-ever zero is
refused too, and a refusal does not advance the history. Availability
cost on a good source: 2^-31 false-refusal odds per word, about 12% per
GiB of output -- immaterial at hardware-wallet volumes.
Kept free of dependencies so the host suite can drive it with
deterministic sequences ('make health', part of 'make tests'): stuck,
period-2, first-zero, recovery-after-refusal, history-laundering, and
the documented limitation that period-3 repetition passes (raw-source
statistical validation stays an integrator obligation).

Fixes, inside libngu, the class of bug behind the 2026-07-31 Coldcard
'limited entropy' advisory: the old '#ifndef MICROPY_HW_ENABLE_RNG'
guard let boards defining it as 0 silently link upstream MicroPython's
PSEUDO-random rng_get() fallback, and treated it as a TRNG.
Backend selection is now fail-closed with exact-value attestations
(an undefined macro evaluates to 0 in #if, so absent, zero, and wrong
values all fail alike):
- STM32 stops unless -DNGU_STM32_RNG_GET_IS_HARDWARE=1 attests that the
linked rng_get() reads the TRNG peripheral -- a preprocessor cannot
detect which rng_get() got linked, so a human must. In-repo, only
STM32L496GDISC earns the flag (it sets MICROPY_HW_ENABLE_RNG=1);
command-line BOARD overrides build without it and fail closed.
- ESP32 stops unless -DNGU_ESP32_RNG_IS_TRUE_RANDOM=1 attests a true
entropy source is active before the first RNG call: per Espressif
docs, esp_random() is otherwise pseudo-random -- and a PRNG passes
any repetition check. No build defines it yet; the target is
intentionally unavailable pending hardware validation.
- Linux uses getentropy() (random(3) is not a CSPRNG); macOS/FreeBSD
keep arc4random(). Unknown targets fail the build; the dead
0x5a5a5a5a fallback is gone. All backends share one contract,
bool chip_trng_read(uint32_t *out), so every failure -- including
STM32's timeout-conflated zero words, refused outright -- flows
through a single wipe-then-raise boundary.
Yasmarang (104-bit non-crypto state, public constants, 'whitening'
that whitened nothing) is deleted. All output paths -- bytes(),
uint32(), uniform(), and every private key k1.c generates -- flow
through one function: HMAC_DRBG auto-seeded on first use with 64 bytes
of raw entropy (SP 800-90A minimum is 48), each output word XORed with
a fresh checked entropy word, entropy_health rule on every read.
Previously uint32() and uniform() XORed raw TRNG with no health check
at all, and the check itself reset each call.
reseed() now accepts bytes-like of any length and MIXES into the full
DRBG state -- the old version stored 32 bits into yasmarang_pad, so
the 40 bytes of secure-element entropy Coldcard feeds at boot were
truncated to 4. Sources compose; the legacy int form remains (4-byte
LE), documented as discouraged.
Also: negative bytes() counts rejected (previously wrapped through
vstr_init_len and wrote ~4GB over the heap); uniform() rejection mask
fixed to (1 << bits) - 1 (was one bit wide, doubling rejections);
state is unsynchronized by design, so builds with threads but no GIL
are refused at compile time and the unix test variant builds without
threads; module header and random.h state the serialization contract.
regression-test the compile-time gates ('make gates')
